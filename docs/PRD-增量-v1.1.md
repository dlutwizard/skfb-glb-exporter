### 0.1 现状基线（已读代码 + 实测，作为指标起算点）

**发布物体积**（实测）

| 组成 | 体积 | 占比 | 说明 |
|---|---|---|---|
| `_internal/node.exe` | 84 MB | 46% | 只为跑 `convert.mjs`（osgjs→GLB）与 `decrypt_worker.mjs`（WASM 解密） |
| `_internal/node_modules`（sharp + @img） | 30 MB | 17% | 仅用于 `createImageBitmap` 垫片（JPEG 解码）+ PNG 编码 |
| `_internal/libvips-42.dll` + `libvips-cpp` | 19.3 MB | 11% | **重复副本**，`node_modules/@img/sharp-win32-x64/lib/` 下已有一份一模一样的 |
| `_internal/engine`（含 `binzDecrypt.exe` 18.7 MB） | 19 MB | 10% | 下载引擎；`binzDecrypt.exe` 本身是 Node 单文件二进制 |
| Python 运行时 + Tcl/Tk + OpenSSL | ~21 MB | 12% | 必需 |
| **onedir 合计 / green zip** | **181 MB / 81.5 MB** | | |

**性能基线**：单文件 exe 启动 39.6 s（每次解压 181 MB）／onedir 启动 1.7 s → 已定型为「只发 onedir zip」。
**内存基线**：**尚未测量**（见 R5，本次必须先量出来才能谈优化）。
**功能现状**：多链接并行（1-5 并发）、贴图描述解密、GLB 导出、默认目录自适应、配置写 APPDATA 兜底、certifi 修 TLS；`--selftest / --env / --run` 三个命令行模式可用。
**工程现状**：无版本常量、无 CHANGELOG、无构建脚本（`build/` 里是 PyInstaller 手搓产物 + 手工 spec）、`使用说明.txt` 内写死体积数字（"150MB/40秒"，已与实测不符）。

## 1. 版本目标与成功指标

### 目标（3 个正交目标）

1. **可辨识** —— 版本号成为程序的一等公民：用户能看见、程序能自证、构建能追溯。
2. **可迭代** —— 建立「改代码 → 出包 → 写日志 → 可回滚」的最小发布流水线，任何一版都不需要推倒重来。
3. **更轻更快** —— 用可测量、可回滚的方式拆掉 181 MB 里最肥的依赖，同时不牺牲「解压即用」。

### 成功指标（可量化，全部可在 v1.1 验收时复核）

> **单位口径（重要）**：本文所有「MB」与 `build/build.py` 一致，一律按 **MiB**（1 MB = 1024×1024 B）计。实际 v1.1.0 产物实测：onedir **150.1 MiB**、zip **70.16 MiB**。

| # | 指标 | 基线 | v1.1 目标（= build.py 门禁） | 终极目标（v1.3） |
|---|---|---|---|---|
| M1 | onedir 体积 | 181 MiB | **≤ 160 MiB**（`ONEDIR_LIMIT`）<br>实测 **150.1 MiB** | ≤ 62 MiB |
| M2 | 分发包 zip 体积 | 81.5 MiB | **≤ 72 MB**（`ZIP_LIMIT`）<br>实测 **70.16 MiB**<br>*66 MB/strict 为 v1.2 目标值：需削减 `node.exe` 才能达到，而 `node.exe` 已 UPX、实测不可压* | ≤ 30 MiB |
| M3 | 冷启动到窗口（onedir） | 1.7 s | **≤ 1.7 s（不退化）** | ≤ 1.2 s |
| M4 | 单模型转换峰值内存（RSS） | **未测** | **完成基线测量并写入文档** | 相对基线下降 ≥ 40% |
| M5 | 版本号一致性 | 0 处（无版本） | 4 处一致：窗口标题 / 关于面板 / `--version` / exe 文件属性 | 保持 |
| M6 | 回归底线 | — | 6 个样本模型（4K 贴图 / 骨骼绑定 / 多材质 / 大面数 / 无贴图 / 短链）导出 GLB 成功率 100%，与 v1.0.0 输出结构一致 | 保持 |

#### 3.1 R6 决策：Node 依赖怎么削

**现状依赖链（三处，互相独立）**

| 依赖 | 体积 | 干什么 | 能否纯 Python 替代 |
|---|---|---|---|
| `node.exe` | 84 MB | ①`extlib/osgjs2gltf.js`（133 KB，osgjs→GLB，含骨骼/动画/多材质）②`tools/wasm/decrypt_worker.mjs`（binz 解密） | ①**难**（移植量大、回归风险高）②**中**（wasm 需运行时） |
| `sharp` + `@img/libvips` | 49 MB（含 19.3 MB 重复副本） | 仅做 JPEG/PNG 编解码（`createImageBitmap` 垫片 + PNG 输出） | **容易**：Pillow 直接对应 |
| `binzDecrypt.exe` | 18.7 MB | binz 解密的 Node 单文件后端（WASM 路径失败时的兜底） | 中 |

**推荐方案：三步走，先摘低垂果实，重写放后面（理由见下）**

| 阶段 | 动作 | 体积影响 | 风险 | 工期量级 |
|---|---|---|---|---|
| **v1.1（本次）** | ①删除根目录重复的 `libvips-42.dll` + `libvips-cpp`（构建脚本剔除，`sharp` 从 `node_modules/@img/.../lib/` 正常加载）②剔除 `@img/sharp-wasm32` 等非 win32-x64 冗余包；**`@img/colour` 明确不删**——`sharp/dist/colour.cjs:6` 与 `colour.mjs:6` 直接 `require('@img/colour')`，`colour` 是 sharp 核心模块（非可选），删除必致 `Cannot find module` ③`使用说明.txt` 中"150MB/40秒"改为脚本注入的真实数字 | **−31 MiB**（181 → **实测 150.1 MiB**；zip **实测 70.16 MiB**） | **极低**：纯删重复/未使用文件，不碰代码逻辑 | 0.5 天 |
| **v1.2** | Pillow 接管全部图像 I/O：Python 侧完成 JPEG 解码 + 描述解密（移植 `extlib/descramble.js`，纯数组运算，无平台依赖）+ PNG 编码，把 RGBA 原始像素传给 Node；Node 只保留 osgjs→GLB | **−49 MB**（含 v1.1 已省） | **中**：需保证解密结果与 JS 版逐像素一致（用样本图做哈希断言） | 3-5 天 |
| **v1.3** | Python 版 GLB 写出器（现有 `osgjs_convert.py` 已能纯 Python 解出几何并导出 OBJ/MTL，缺的是 glTF 2.0 打包层 + 骨骼/动画），去掉 `node.exe`；解密改走 wasm/纯 Python，评估去掉 `binzDecrypt.exe` | **−103 MB**（181 → ≤62） | **高**：`osgjs2gltf.js` 133 KB 含 skin/anim/morph，重写必须靠 R5 基线 + M6 套件守住不退化 | 2-3 周 |

**为什么不全押 v1.3 一次到位**：用户的核心诉求是"改动不推倒重来"。v1.1 用 0.5 天拿到 12% 瘦身且几乎零风险；v1.2/v1.3 每一步都有可回滚的中间态和可对比的产物。反之若 v1.1 直接重写转换器，一旦骨骼/动画模型导出退化，等于把已能用的 v1.0.0 变成半成品。
**备选（不建议）**：改用更小的 JS 运行时或编译期裁剪 node.exe —— 收益不确定、破坏"解压即用"的自包含性，且 node.exe 已 UPX 过，进一步压缩会显著抬高杀软误报率。

| ID | 需求 | 验收标准 |
|---|---|---|
| **R7** | **配置与程序分离（升级不丢设置）**：`config.json` 默认写 `%APPDATA%\Sketchfab下载器\`，程序目录内配置降级为"便携模式"（存在则优先，无则用 APPDATA）；输出目录不受升级影响 | 解压新包覆盖旧目录后，上次保存目录与并发数仍生效 |
| **R8** | **文档随版本走**：`使用说明.txt` 改为构建时从模板生成（注入版本号、真实体积、CHANGELOG 摘要） | 说明文档里不再出现任何写死的体积/版本数字 |

## 4. 非目标（本次明确不做）

1. **不做安装包 / 静默自动升级服务**（无服务器、无签名证书，收益低风险高）。
2. **不重写 GUI**，继续用 tkinter；不做主题改版。
3. **不改下载协议核心**（`sketchfab-cli-main` / `dist_engine/main.py` 的解密与抓取逻辑），只做依赖替换。
4. **不做代码签名、不做杀软白名单申报**（成本与资质问题，仅文档说明）。
5. **不做多平台**（macOS / Linux / Win7 兼容性专项）。
6. **不改输出格式约定**（GLB 仍是唯一成品，`.gltf` 仍是备胎）。
7. **不做账号 / 付费模型 / 需登录模型的下载**。
8. **不引入 CI 云服务**，构建流水线仅本地脚本。

## 5. 待确认问题（请主理人转所有者）

1. **是否愿意把代码发布到 GitHub？公开还是私有？仓库地址？** —— 直接决定 R9 走方案 A（网盘/任意 URL）还是方案 B（GitHub Release）。**注意合规冲突**：`使用说明.txt` 第九节自己写了"本工具绕过 Sketchfab 下载按钮，公开挂出去可能违反用户协议"，因此**不建议公开仓库**；若要发布，建议私有仓库 + 仅发布 Release 包。

4. **迭代节奏确认**：v1.1 只做「版本体系 + 构建脚本 + 零风险删重复（181→≤160 MB）」，重写转换器放到 v1.2/v1.3 —— 接受吗？还是希望 v1.1 一次把 Node 全去掉（工期 3 周左右、回归风险显著上升）？
5. **单文件 exe（82 MB / 启动 40 s）还要继续发布吗？** 建议从发布物移除或标为实验性。
6. **M4 内存指标的目标值**：先按"完成测量、后续版本相对下降 ≥40%"设，还是所有者有明确绝对上限（如"转换时不超过 1 GB"）？
7. **最低目标环境**：是否需支持 Win7 / 32 位系统 / 无独显老机器？影响 Pillow 与 PyInstaller 的兼容取舍。
